# 0034 — Dependabot keeps the lock file and the Actions current

**Status:** Accepted. Not yet confirmed against a real Dependabot run; see "To confirm".

## Context

`requirements-lock.txt` holds exact versions and CI installs with it (`pip install -c
requirements-lock.txt`). The file is regenerated by hand (`pip freeze --exclude-editable`). The
GitHub Actions in `ci.yml` are pinned by tag (`@v4`, `@v5`). Pinning makes the build reproducible,
and it also means nothing upgrades itself: a new release, or a vulnerability fix, only arrives when
the author remembers to regenerate. The repository had no `dependabot.yml`, Dependabot security
updates were off and vulnerability alerts were not enabled, so a known vulnerability in a pinned
dependency would not have been reported.

The CookingTime repository has the same pinning and a Dependabot setup. Its first version opened 21
pull requests at once, most of them duplicates, and its pull requests failed the locked restore
because Dependabot regenerated a lock with a different SDK. Both lessons are used here.

## Decision

1. **`.github/dependabot.yml` covers two ecosystems: `pip` and `github-actions`**, both weekly, with
   at most 3 open pull requests each.
2. **Minor and patch updates are one grouped pull request per ecosystem.**
3. **Major updates of Python packages are ignored.** A new major version of pydantic, flask or mcp is a
   migration to plan, not a change to merge from a bot. This setting does not hold back security updates.
4. **CI is the gate.** A Dependabot pull request runs the same workflow as any other: install with
   the lock, the suite on Python 3.11 to 3.14, ruff, the import contracts and mypy. A person reviews
   and merges it. The `main` ruleset still requires the admin bypass to merge.
5. **Repository settings:** vulnerability alerts and Dependabot security updates are turned on, and the
   `dependencies` and `ci` labels exist so Dependabot can apply them.
6. **The Dockerfile is left out.** Its base image is `python:3.11-slim` and 3.11 is the supported floor
   (ADR 0033). A bump to a newer tag would change what is supported, which is a decision and not an update.
7. **The Actions stay pinned by tag.** Pinning them to commit SHAs is a separate change, not part of
   this one. Dependabot updates tag-pinned Actions too.

## To confirm

- **Whether Dependabot reads `requirements-lock.txt`.** The file has a non-standard name and is a
  constraints file. If Dependabot only reads the ranges in `pyproject.toml`, the pip block would not
  move the pins. The first run's log will show which files it found, and this ADR is updated with the
  answer.
- **Whether an updated pin can fail the install.** The lock was incomplete once (ADR 0033), and a test
  keeps it in step with `pyproject.toml`. A Dependabot pull request that breaks the install would be
  caught by CI, which is what the gate is for.

## Consequences

**Easier**

- Vulnerabilities in pinned dependencies are reported, and fixes arrive as pull requests.
- Updates arrive weekly as at most one Python pull request and one Actions pull request.

**Harder**

- A weekly pull request to review. If the pip block cannot update the lock, it will do little and the
  hand-regenerated lock stays the real process.
- Merging still needs the admin bypass.
